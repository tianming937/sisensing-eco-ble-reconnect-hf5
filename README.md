## 能改善什么

hf8 针对前版“走远断连后回到范围，灭屏/亮屏都可能无法恢复”的两条故障链进行改造：

| 故障/需求 | hf8 实现 | 验证边界 |
|---|---|---|
| 多个重试入口反复启动扫描，引发系统限流 | 幂等 PendingIntent 扫描租约、扫描所有权检查、Alarm 去重 | 源码/模型通过；真实蓝牙栈待测 |
| 扫描错误码 6 后立即重试 | 首次 120 秒冷却，30 分钟内再次发生提升至 300 秒，重试入口受冷却限制 | 模型通过；不同三星系统需实测 |
| 内部关闭连接被误当成用户永久暂停 | 传输清理不再改用户暂停标记；显式停止保留持久化意图 | 源码/模型通过；并发回调待真机压力验证 |
| 仅状态回调显示连接就误判恢复 | `STATE_1` 只算待验证；有效算法数据后确认，6 分钟验证超时 | 模型通过；新鲜度与长时间读数仍需实际验收 |
| 前台服务前置条件不足导致崩溃循环 | 用户解锁/权限检查、异常防护，失败返回非粘性启动；r2 修正系统版本边界 | Android 12 MuMu 通过；Android 14+/OTA 待测 |
| 诊断写入过密 | 有效数据事件按分钟聚合，hf8 独立匿名审计目录 | 静态检查；长时间保留/耗电待测 |

同时保留系统唤醒、过滤式后台扫描、有界唤醒锁，以及 hf6 的分页补传、冷启动设备恢复、血糖分享请求保护、修改资料防崩和未知算法拒绝保护。不更改原生血糖算法、BLE 协议、GATT UUID 或数据库结构。

**不能解决的物理/平台边界：** 探头不在范围、停止广播、失效、被其他设备占用、权限不足或系统拒绝后台执行时，软件无法保证立即连接。冷却期间等待是设计行为，不应连续点击连接绕过。

## 源码与构建

```text
patches/v16.1-hf8-over-hf6.patch  # 合并的 hf6→hf8-r2 增量；无需安装/发布 hf7
```
