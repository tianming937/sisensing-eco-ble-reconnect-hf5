- Apktool 2.9.3 构建成功；

- APK v1/v2/v3 签名验证通过；
- hf4 → hf5 非签名 ZIP 条目共 290 项，新增 0、删除 0；仅 `AndroidManifest.xml`、`classes.dex`、`classes5.dex` 发生预期变化。

`apksigner` 会提示 `META-INF/services/*` 没有受到 v1 JAR 签名保护；同一 APK 同时通过 v2/v3 全包签名。该提示来自原包的服务资源布局，不是 hf5 新增文件。

## 2. MuMu Android 12

完成：

- hf4 → hf5 覆盖升级，`versionCode 36 → 37`；
- 连续 5 次强制停止后冷启动，进程均存活；
- 正式包冷启动约 1.2 秒；
- 短信登录页和密码登录页双向切换；
- 四套已知算法在目标进程中加载对应 ARM 原生库，4/4 通过；
- 未知、空、`null` 算法标识均返回 `null`，3/3 通过；
- 未发现 `VerifyError`、`UnsatisfiedLinkError`、`SIGABRT`、Java `FATAL EXCEPTION` 或 ANR。

MuMu 没有真实 BLE 探头，且测试实例无法可靠进入真实深度灭屏，因此不能用来证明 GATT 或灭屏重连。

2. 三星 `dumpsys bluetooth_manager` 的 GATT 历史；
3. App 私有重连事件文件；
4. 电池历史中的屏幕状态；
5. `dumpsys activity exit-info`。

## 5. 信号质量

35 个连接样本：

| 指标 | RSSI |
|---|---:|
| 最好 | -57 dBm |
| 中位数 | -90 dBm |
| 最差 | -103 dBm |
| ≤ -90 dBm | 18/35 |
| ≤ -100 dBm | 8/35 |

这说明当前剩余的主要问题是射频链路很弱，而不是重连状态机完全停摆。实际观察中出现过 `status=133`、`147` 和弱信号下刚连上又断开的抖动。

## 6. 崩溃审计

系统历史中能看到两组旧问题：

- hf5 安装前的 E112G 算法 `VerifyError` / native `SIGABRT`；
- 安装后早期的 `xq2` / ViewPager2 趋势页 Java 类校验异常。

在最后一次该 UI 异常之后至观察截止，没有新的 App 退出、算法 `VerifyError`、`SIGABRT` 或 ANR。`xq2` 是与 BLE 重连不同的 UI 路径，应继续作为已知限制观察。

## 7. 当前结论

证据支持以下结论：

- hf5 的断线自动重连状态机在该真机观察窗内持续工作；
- 灭屏状态下确实发生了重试并最终恢复，不是每次都依赖亮屏；
- 36 次可识别断连都最终恢复，但恢复时间会随信号和蓝牙栈状态波动；
- 软件无法解决物理信号过弱或探头不广播；
- 下一项最有价值的安全改进是“断连超过 5 分钟主动告警”，而不是进一步压缩重试间隔。

这些数据来自单台手机的观察性测试，不构成医疗验证、监管认证或普遍成功率保证。
